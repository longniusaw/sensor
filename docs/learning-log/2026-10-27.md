### 2. 排查 SLAM 生命周期问题

初次启动后，发现 `/slam_toolbox` 节点处于 `unconfigured` 状态，并且没有订阅 `/scan`，也没有发布 `/map`。

通过以下命令检查节点状态：

```bash
ros2 lifecycle get /slam_toolbox
ros2 node info /slam_toolbox
```

随后手动执行生命周期转换：

```bash
ros2 lifecycle set /slam_toolbox configure
ros2 lifecycle set /slam_toolbox activate
```

日志显示节点依次进入 `Configuring`、加载 Ceres 优化器、进入 `Activating`，并输出：

```text
Registering sensor: [Custom Described Lidar]
```

再次检查后，节点状态为：

```text
active [3]
```

节点已订阅 `/scan`，并发布 `/map`、`/map_metadata`、`/pose` 和 TF 等相关话题。

### 3. 验证地图输出

执行：

```bash
ros2 topic echo /map --once
```

得到的地图消息包含：

- 坐标系：`map`
- 分辨率：约 `0.05 m/cell`
- 初始栅格尺寸：`98 × 78`
- 地图数据：大量 `-1`（未知区域）

这说明地图消息已经生成，但不能仅凭话题存在就认定建图质量正常。地图是否正确，还需要结合 RViz 显示、机器人运动和环境实际结构验证。

### 4. 初步理解 SLAM 数据链路

今日梳理了在线建图的基本关系：

1. 激光雷达通过 `/scan` 发布距离和角度数据。
2. 里程计通过 `/odom` 提供机器人运动估计。
3. TF 将 `map`、`odom`、`base_link` 和 `laser_frame` 等坐标系联系起来。
4. `slam_toolbox` 使用激光扫描和运动信息进行扫描匹配与地图构建。
5. 最终通过 `/map` 发布栅格地图。

## 三、发现的问题：地图出现障碍物重影

### 实际现象

Gazebo 中的场景包含两根柱子和一面墙。

- 小车最初正对两根柱子，RViz 地图能够显示相应障碍物。
- 操纵小车运动并转圈后，RViz 中出现了额外的柱状障碍。
- 最终地图中有三处柱状障碍，其中两处与预期位置相符，另一处为疑似重影。
- 操作过程中观察到机器人模型似乎发生过一次跳变。

### 当前判断

该现象可能与连续扫描之间的位姿估计或扫描匹配不一致有关，但目前尚未确认根因。

待排查的方向：

- `odom → base_link` 是否发生不连续变化。
- `map → odom` 是否出现不合理的瞬时修正。
- `base_link → laser_frame` 是否保持固定。
- `/scan` 的数据与时间戳是否正常。
- SLAM 扫描匹配是否将同一根柱子的不同帧扫描对齐到了不同位置。

**注意：** 地图保留先前观测本身是正常的。当前需要确认的是，新旧柱状障碍是否确实来自同一根真实柱子，以及它们为何被放置在不同位置。
